My geocoder answers every query from one file. No database, no server farm. It runs on a Cloudflare Worker or in a browser tab. A query like "Sam sam tea shop Pathanapuram Kollam" still has to be understood before it can be answered: which words are the shop, and which word is the town?

## The obvious answer: libpostal

The usual tool is [libpostal](https://github.com/openvenues/libpostal). Pelias uses it. It labels each word of an address (house number, road, suburb, city, postcode) and it needs about 2 GB of model data. That doesn't fit in a file you load in a browser.

So I trained a small one of the same kind: an averaged structured perceptron with Viterbi decoding, the model libpostal uses. Features hashed into 32,768 slots, one byte per label, 288 KB in total. The training data came from 486,902 OpenStreetMap objects in India that already carry `addr:*` tags, written out the ways people type an address.

## The first benchmark lied

On 3,000 generated test addresses it got 58 % of whole addresses right against libpostal's 26 %. I almost published that.

Then I tested on addresses people had actually typed (OpenStreetMap `addr:full`). The gap nearly vanished. My test data came from the same generator as my training data, so of course the model looked good on it. After fixing the generator (suburbs, "near …" landmarks, "City - PIN") it labelled 71.7 % of typed words right against libpostal's 67.0 %, on a small set of 260 addresses.

A win, on paper.

## Why I deleted it

Two things were wrong with it.

**It was a copy.** The model is a design from the early 2000s. Making it smaller is engineering, not a new idea.

**It ignored what the file already knows.** A tagger guesses that "Kollam" is a city from the shape of the word and its neighbours. But the file I search holds every town in the country, how important each one is, and which places lie inside it. Guessing what the file can tell me is backwards.

So the reader now asks the file:

1. Take the last one, two or three words as the town, longest first.
2. Look each reading up. It stands when the file holds a town of that name of some note, and places matching the other words lie inside it.
3. If no reading stands, search the query as written.

No model, no training data, and it works in every country the file covers, not only India.

## Not new either

I checked before calling it mine. It isn't. Nominatim's query code (`token_assignment.py`) lists every way to split a query into a name and its address parts, and checks each split against its database. Google patented the idea in 2012 (US8156099). What is different in my version is only where it runs: from one static file, with no database server and a fixed read budget per query.

## The numbers

India gold queries with their commas removed, same file:

| Query class   | Reading from the file | 288 KB tagger | Photon |
| ------------- | --------------------- | ------------- | ------ |
| OSM addresses | 95.0 %                | 95.0 %        | 88.5 % |
| OSM POIs      | 82.0 %                | 80.5 %        | 85.5 % |
| Overture POIs | 92.5 %                | 93.0 %        | 12.5 % |

Same accuracy within noise, p95 latency 29 ms against 20 ms, and one less model to train and ship.

## The lessons

- Test on data your model did not come from. My first number was 2× too kind.
- Before training a model to guess something, check whether your own data can just answer it.
- Before calling something new, read the source of the systems you are competing with. Nominatim had this years ago.

The full benchmark is on the [geolith docs](https://docs.search.geolith.app/benchmarks/town-reading).
